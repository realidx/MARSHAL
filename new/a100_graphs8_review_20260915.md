# 双 A100：graphs 并发 4 / 8 对比

输入：`new/local_data/social_runs/social_probe_20260915/perf-graphs4-20260914-130137/` 与 `perf-graphs8-20260914-131556/`。

## 配置选择

后续独立 B/P 诊断采样采用 CUDA graphs、每卡 8 个请求、每卡一个模型副本（TP=1），GPU 6/7，继续使用 1024 输出预算。self-play 可以从此并发起步，但其完整局吞吐和接口仍需实测；不将 B/P 性能对照等同于 self-play 验证或训练验证。本轮不继续扩大性能搜索。

## 实测

| 项目 | 每卡并发 4 | 每卡并发 8 |
|---|---:|---:|
| 请求／HTTP 完成 | 32/32 | 32/32 |
| 基础设施失败／采样超时 | 0/0 | 0/0 |
| 输出 token 总量 | 29,991 | 30,080 |
| 采样墙钟，不含服务启动 | 104.395 秒 | 64.008 秒 |
| 双卡合计输出吞吐 | 287.283 tokens/s | 469.945 tokens/s |
| 单请求耗时中位数 | 25.492 秒 | 27.606 秒 |
| 合规原生工具提交 | 8 | 8 |
| 长度截断 | 24 | 23 |
| 其他格式失败 | 0 | 1 |

吞吐提高 63.58%，采样墙钟减少 38.69%；单请求中位耗时增加 8.29%。输出量只增加 0.30%，速度差并非靠少输出解释。对离线批量采样而言，这个吞吐收益值得采用并发 8。

两轮请求文件 SHA256 相同：`e51f93b98fcac38f4358df3b71743e75bcb66e8d5552e274a3826a315be734df`。模型三份配置哈希、软件版本、GPU 编号、输入／输出预算和执行模式相同；服务 max_num_seqs 与客户端 workers 一起从每卡 4 调为 8。请求种类、seed 和重复数均不变。

并发 8 两卡均成功 capture，分别约 20 秒和 11 秒，各报告占用约 0.31 GiB；`use_async_output_proc=True`。没有 ERROR 或 Traceback。日志观测到的 KV cache 使用率最高分别 9.8% / 10.7%，Swapped 始终为 0，未见显存不足。这里的 KV cache 使用率不是整卡显存利用率。服务结束时仍有未显式销毁 NCCL process group 的警告，与并发 4 一致，不是采样失败。

两轮均没有附带同期 CPU/GPU 采集，32 请求也包含启动后首批请求和收尾，不是稳态大批吞吐测量。可以据此选择当前实用配置，不将 63.58% 当作所有负载下的固定加速比。不同并发会改变动态 batch 和执行顺序；固定 seed 不保证逐字一致。
