## 截断在什么位置

416 次回答全部有 `raw_message.reasoning_content`，thinking 模式已生效，解析器预检通过。273 次 `finish_reason=length` 的 `completion_tokens` 全部正好为 1024。

- **260 次截断只返回 reasoning，没有最终 content 或工具调用。** 此处根据 HTTP 字段分类；解析器会移除思考边界标记，不能仅凭 content 为 null 区分“还未输出闭合标记”与“恰好在思考结束处耗尽预算”。
- 另 13 次已开始最终 content，但工具提交没有完整完成。

因此主要瓶颈是大量输出预算用于思考，不是工具接口超时。其原因也不只是任务需要更长的有效推理：精读样本有大量重复陈述、来回反问、误读状态和旧 belief 后反复讨论。

例如 bridges `fdcef144ef63d8c67397` sample 0，思考多次重复“没有关于 Harbor 的新证据，仍保留 want/avoid”，最后开始 SUBMIT_BELIEFS JSON 时截断。L0 `d335ef92e22848f206fc` sample 0 也重复陈述同一个维持结论，直到最终 JSON 中途用完预算。这类样本确实存在“有结论但没有及时提交”；不能推广成所有截断只差几个 token 就能正确。

原 P `d71af8ccfae85c56f205` sample 0 则反复讨论自我承诺与对方承诺，重新把已知偏好说成未知，还未形成完整动作选择就耗尽预算。增加长度是否有收益，需要独立检验，不能从截断率直接推导。

一个具体的“标签正确、理由错误”例子：bridges `349c390e78f9013b1ce1` sample 1。

- 正确旧 belief 是 `[want, neutral, avoid]`，favored=want。
- 模型先声称新的拒绝证据没有提供相关信息。
- 随后把旧 belief 的 favored=want 解释成已知 wants Harbor，因此提交 `[want]`。
- 最终恰好命中 gold，但 favored 表示相对倾向，不代表其他可能性已经被排除。不能用这条解释直接制作 SFT 正例。

## 训练判断

Thinking 改善了部分 B 的正奖励与组内差异，不能因为截断率高就断言 GRPO 无法改善它；本轮 train 有 10/31 个混合组，已经比 nonthinking 的 3/31 多。

但 **thinking + 1024 目前不能直接支撑 B/P 与 self-play 大规模混训**：P 几乎都截断，self-play 没有可用终局组。混入更多 self-play 不能补救缺失回报。该结论不要求把所有 base model 的错误都先修好。

后续应明确区分两项工作：B 的少量短 GRPO 是否能利用已有信号学会在预算内完成任务；self-play 的推理模式／输出预算如何与完整局目标兼容。若要改成 2048，应作为用户明确选择的少量预算对照，不能直接扩大整套测试或悄悄改变正式训练原则；即使长度增加，也不保证 reasoning 变正确。若选择短 SFT 冷启动，同样需要明确改变原 RL 起点，并独立核验解释，不能把上述碰巧命中的错误 reasoning 用作正例。
